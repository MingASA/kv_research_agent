# 质量与原生工具任务

**当前 FP8 配置没有获得通用生产质量接受。** 数学答案抽取分数接近或略升，与长文、多跳问答、代码补全代理下降同时存在；原生工具总匹配率相同，也掩盖了逐题互换与生成长尾。已完成的是原始预测完整性、官方评分复核和限定样本上的质量代价测量，不能把它们称为“质量通过”。

下文主表为原FP8-XQA的C128配对，保持原分数。第46新FP8-BF16Q完整1719现已独立验收，LongBench48.0393290%、对现代BF16−2.1491572pp，未观察整体修复；新对旧FP8之差区间跨0，不判显著更差或等价。完整三配置与停止决定见[06补充](06_第46条BF16Q完整质量与停止决定.md)。

## 3. 代码代理的现象，不应被“评分器问题”掩盖

旧C8 XQA完整代码100题官方评分逐题复核：LCC4改善/8退化/38持平，完整匹配计分行13→10；RepoBench7改善/5退化/38持平，完整匹配9→10。官方`code_sim`选首个不含反引号、`#`、`//`的行做字符串相似度；“找到合格空行”与“没有合格行默认空串”不同。[代码模式正式分析](../experiments/production-xqa-quality-full1719-20261026/CODE_ERROR_ANALYSIS.md)、[v3逐题原件](../operations/20261026T075846Z/xqa_code_quality_patterns_v3.json)

早期v1/v2把上述两类合并，现已更正并保留旧文件。LCC有效计分空串1→3，开头解释性前缀0/50→3/50；没有整段输出全为空白的样本。index5的FP8解释性长句没有给期望代码行，index17/20有解释和空行；不能因后面另有围栏就认定代码正确，也不能把−5.38pp只归为可忽略评分噪声。这支持“该冻结代码补全协议下有格式/指令遵循风险”，尚不证明完整代码执行或agent成功率下降多少。上述模式数量属于旧C8，未移植为C128逐题模式计数。

若产品改变prompt、提取器或任务执行协议，需另立BF16/FP8相同协议并保留原结果；修改评分器以消除负分不是质量修复。

## 5. 流式工具接口的独立缺陷

旧streaming run `prod-tools-bf16xqa-bfcl258-c128-r0-20261027a` 在BF16首warm API门槛失败，尚未开始AIPerf、没有FP8结果。HTTP200/tool_calls/DONE都有，但标准delta拼接后参数JSON无效、含重复后缀；55原始文件与FAILED保留，实际.096657004GPU-h已计费。[独立失败证据](../operations/20261026T075846Z/native_tool_stream_failure_a_independent_evidence_v1.json)

CPU复现确认原C++增量参数输出有键排序缺陷：合法模型JSON按`prompt,width,height,image_format`逐步到达时，`nlohmann.dump`按键排序改变已经发送的前缀，旧sent长度继续切片，越界异常又被吞。原Base/Qwen25/partial-JSON核心和API最终flush函数体未改，chunk1/2能精确产生旧坏wire；其他分块可生成合法却错误的参数，排序键控制9种分块全对。[CPU复现](../operations/20261026T075846Z/native_tool_stream_CPU_late_key_defect_v2.json)

**确定的是实现缺陷和复现能力，未确定的是旧H800请求的原始pre-parser token顺序。** 原token流未导出，不能称完全历史逐token重放。该缺陷属于共享baseline接口，不归因KV量化；没有热改binary或客户端补字/去重。后续buffered全JSON成功只证明另一协议的契约，不能认证streaming正确。生产支持需对实际流式工具增量、拆包、flush和调用方解析做独立修复验收。
