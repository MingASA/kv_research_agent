# 当前最高项目目标：生产是否值得完整支持 KV Cache 量化

来源：2026-10-26 本会话用户最新明确指令。此文件解释并覆盖旧文档中论文/科学矩阵优先、固定FA2或强行固定输出优先的部分；历史记录不重写，安全与真实证据要求继续有效。

## 目标与投入原则

项目是生产实验，最终决定 xLLM 是否、以及以哪些可维护的格式/后端/配置完整支持 KV Cache 量化。依据是真实服务的质量、容量、成功率、吞吐/延迟、每GPU服务成本、部署与维护复杂度。不是为论文寻找显著性，不以填满实验矩阵、做出量化加速或完成单次 AIPerf 为目标。

请求、benchmark/workload、GPU、后端算子和服务配置均应代表生产推理引擎会实际面对的情况。对不具生产代表性的场景不安排GPU实验；单卡与多卡规模差异允许。微基准只有在解释生产故障/瓶颈或验证具体可落地修复时才做，成本受该决策需要约束。

## 生产评估范围

- 请求：真实对话、长文/RAG、代码/多轮工具调用；保留自然停止、明确生成上限与完整上下文。主性能请求不强制 ignore_eos，不强制把无关文字拼成16K/24K。最大输出长度与实际生成长度同时记录，不把产出更长造成的tokens/s增幅冒充同等服务质量收益。
- 原计划workload须对齐 `vendor/AIperf文档.txt` 与 `plans/RESEARCH_ROADMAP.md`：ShareGPT、BurstGPT、Mooncake conversation/toolagent/synthetic；后续agentic/code。按现存真实文件、来源、许可和语义核实，不能把仅长度/到达统计的trace称为真实文本或完整生产回放。
- 压力：低负载正常服务、符合现实的持续需求和突发/队列、BF16容量开始限制驻留/并发的高压区；报告成功完成的goodput与尾延迟、排队/拒绝/抢占/缓存行为。不要只测两臂都轻松装得下的点，也不要人为追求OOM。到达节奏与prefix/session关系不能被任意切片、shuffle或关闭固定调度破坏。
- 服务：优先可实际部署的Graph、分页、生产调度/token budget、prefix caching与隔离缓存。分别报告cold start与warm steady-state；不能为了简化而永久关掉生产会开启的功能。
- 算子：H800/SM90上实际可用、质量正确且优化过的FA3/XQA/FlashInfer等路径优先。BF16与FP8各使用最佳可部署实现是主生产比较，允许实际不同的kernel，但须明示；不能将其差异说成只改变dtype的因果结论。固定同FA2仅可作为有明确修复价值的辅助诊断。
- 精度：KV存储FP8不等于Q也FP8，更不等于FP8 MMA。Q量化、scale/校准、prefill/decode后端、融合writer均是部署配置的一部分，新增数值近似必须过质量门槛。7B V-only与14B Joint不混算。
- 质量：与实际部署模型/配置一致的GSM8K/LongBench/代码与对话能力代理和必要的生产任务检查；性能工具不代替质量。先小范围检查明显损伤，不能以80条pilot宣称全量通过。质量与SLO容忍度未由用户给数字时标明工程候选阈值，先提供曲线和退化风险，不假称用户已经接受。

## 决策输出

每个候选报告适用工作负载/服务压力、质量损失、成功率、TTFT/ITL/E2E尾部、请求与实际token吞吐、可承载token/sequence、每GPU有效服务成本、运维/源码维护代价。最终给出支持/有条件支持/暂不支持/证据不足及具体条件和待补证据。不能从一个旧FA2低压力结果否定整个量化方案。
